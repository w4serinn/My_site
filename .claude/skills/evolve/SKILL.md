# evolve: waserin個人サイト 自動開発サイクル

以下の手順で **1周だけ** 実行してください。
1周 = 「ROADMAP.mdから次に対応する単位（1〜3タスク程度の意味のある塊）を選ぶ →
実装 → テスト → 軽量セルフレビュー → ドキュメント更新 → commit → push → バックログ更新」です。

---

## 0. 事前チェック

- 作業ブランチは必ず `evolve/cycle-<連番>`。mainにいたら最新化してブランチを作る。
  **人間がmainに取り込むまでは、同じ`evolve/cycle-<連番>`ブランチに複数サイクル分の
  コミットが積み重なるのが正常な動作である**（サイクルごとに新しいブランチを作る
  必要はない）。
- サイクル開始時に `git fetch origin` を実行し、現在のブランチの最新コミットが
  すでに `origin/main` に取り込まれているか確認する。
  取り込まれていれば `git switch main && git pull` で最新化し、新しい
  `evolve/cycle-<連番+1>` ブランチを作り直してから、通常の手順（1節以降）に進む。
- 前回サイクルが未完了（実装済みだがテスト未了、`partial`のまま等）の形跡があれば、
  新しいタスクに着手せず**続きから再開**する。
- ユーザーの手作業らしき変更が混ざっていたら、何もせず報告して終了する。
- `CLAUDE.md` の「サイトのコンセプト」節を必ず確認し、完成の定義と
  content-pendingの扱いから外れた実装をしないこと。

## 1. タスク選定

`docs/ROADMAP.md` を以下の優先順で読み、次に対応するタスクを1〜3個選ぶ。

1. 「バグ修正（最優先）」セクションの未対応項目
2. 現在進行中のページ・要素の未完了サブタスク（上から順）
3. 未着手の確定タスク（`### 確定タスク` セクション、番号順）
4. **確定タスクがすべて完了、または`content-pending`/`blocked`で進められない場合のみ**、
   「新規ページ提案候補」セクションから1つ選んで着手してよい
   （承認は不要。ただし着手前に候補の内容がCLAUDE.mdのコンセプトと矛盾しないか確認する）

- 選んだ候補が `blocked` または `content-pending`（本文入力待ち）で
  今は着手できない状態の場合、そのタスクは一旦スキップし、次の優先順位の
  候補に進む。入力が埋まったことを確認できたら、そのサイクルで再訪してよい。
- **サイズLの項目には着手しない**。S/Mの子項目に分割してROADMAPを書き換えるだけで
  1サイクルとしてよい。
- **1サイクル＝1つの、意味的にまとまった単位**とする。
  複数のROADMAP項目をまとめてよいのは次の場合のみ：
  1. 関連性が強く、比較や統一感が必要な場合
  2. 無関係な項目でも、API使用量を抑えるためにまとめる場合（目安2〜3項目まで）
  いずれの場合も、コミットの差分は項目ごとに分かりやすく分離して書くこと。

## 2. 実装

- 選んだタスクをテスト可能な最小単位で実装する。
- ロジック（計算・状態管理など）は必ず `src/logic.js` に実装し、DOM操作と混在させない。
- 色は `styles/tokens.css` で定義済みのCSS変数を使う。配色自体はまだ確定していないため、
  ループの判断でトークンを追加・調整してよい（CLAUDE.mdの「基本お任せ」方針に従う）。
- ヘッダー・フッターは各ページのHTMLに直接書かず、`<!-- HEADER -->` / `<!-- FOOTER -->`
  のプレースホルダーを使う（`npm run build` が `partials/` の内容を合体させる）。
- ページ内のリンク・スタイルシート・画像などのパスは、`/`から始まる絶対パスを
  **使わないこと**。必ず `{{BASE}}` を前置した相対パスで書く
  （例：`<link rel="stylesheet" href="{{BASE}}styles/tokens.css" />`）。
  `npm run build` が、ページの深さに応じて `{{BASE}}` を正しい相対パスに変換する。
- 本文が必要な箇所（自己紹介の文章、作品の一言説明など）は、
  CLAUDE.mdの「content-pending」節に従い `[要入力：〜について]` を置くこと。
  実装が完了しても、content-pending箇所が残っている限りそのタスクの status は
  `content-pending` のままとし、`完了` にしない。

### タスク実行中にスコープが大きすぎると判明した場合

見積もり（S/M）を超えて作業が拡大しそうだと判明した場合、そのまま続けず以下を行う。

1. その時点で完結し、テストが通る最小の成果があれば、それだけを今回のコミット対象とする
2. 残りの作業を `docs/ROADMAP.md` の新しい子タスクとして書き出す（サイズを再見積もりする）
3. 該当タスクの status を `partial` にして理由を記載し、サイクルを終える
4. 完結した成果が無い場合は、変更を `git stash` で退避し、`blocked` と同様の扱いとする

## 3. テスト・lint

以下を順に実行し、**全て成功させてからコミットする**。

```bash
npm run lint
npm run lint:css
npm run test
npm run build
```

失敗したら修正して再実行。**2回連続で同じ原因で失敗して解決の目処が立たない場合**は：

- 変更を `git stash` で退避
- `docs/ROADMAP.md` の該当項目を `blocked` にして理由を記載
- そのことだけをコミットしてサイクルを終える

## 4. 軽量セルフレビュー（content-pendingチェック）

フルのコードレビューは行わず、以下だけを確認する：

- 今回のdiffで、`[要入力：...]` の形であるべき箇所が、勝手に本文っぽい
  具体的なテキストに置き換わっていないか
- 置き換わっていた場合は元のプレースホルダーに戻し、当該タスクの status を
  `content-pending` のままにする
- それ以外の一般的な実装ミス・矛盾に気づいた場合は、直せる範囲でその場で
  修正するか、`docs/ROADMAP.md` にtodoとして追記する

## 5. ドキュメント更新

- 変更内容に応じて `README.md` を同一サイクルで更新する
- サブタスクを `[x]` にした際は、そのサブタスク行を `docs/ROADMAP.md` から
  `docs/roadmap-done.md` の対応する見出し欄へその場で退避する
  （`content-pending` のタスクはまだ完了していないため退避しない）
- 確定タスクがすべて `完了` になった場合、`docs/ROADMAP.md` 冒頭に
  「枠として完成」した旨を1行追記する（CLAUDE.mdの完成の定義を満たした合図）

## 6. コミット・プッシュ

- 1サイクルの成果を必ず1コミットにまとめ、`evolve/cycle-<連番>` ブランチにpushする
- コミットメッセージ形式：`feat: <内容>` / `fix: <内容>` / `docs: <内容>`
  （content-pending箇所を含む場合は末尾に `[content-pending]` を付与）

## 7. バックログ更新・サイクル終了報告

- 今回選ばなかったタスク、新たに見つけた改善点をROADMAP.mdに反映する
- 以下の内容を `docs/cycle-log.md` に追記する：

```
## YYYY-MM-DD HH:MM
- 実装: (実装した内容)
- レビュー: OK / 指摘N件対応 / スキップ
- lint: ✓ / lint:css: ✓ / test: ✓ / build: ✓
- 次回予定: (次のサイクルで着手予定の項目)
- blocked / content-pending: なし or (内容)
```

追記後、同じ内容をターミナルにも表示する。

## 禁止事項

- mainへの直接commit/push/merge（取り込みは人間がレビュー後に行う）
- PRの作成・マージ（`gh pr create`、`gh pr merge`等）を自分で実行すること。
  取り込みの判断と実行は必ず人間が行う
- 履歴改変（`rebase -i`、force push、`reset --hard`）— evolveブランチ上でも禁止
- テストが通っていない状態でのcommit/push
- ROADMAPにない大規模リファクタリング
- content-pending箇所への本文の無断創作
- ROADMAPを経由しない新規ページの追加
